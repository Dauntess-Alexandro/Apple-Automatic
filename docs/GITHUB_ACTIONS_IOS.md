# Универсальная сборка iOS через GitHub Actions

Файл `github-actions-ios.yml` рядом с `codemagic.yaml` — переносимый шаблон.
Он собирает и подписывает Flutter и нативные Swift/Objective-C приложения с
существующим `.xcodeproj`. В репозитории может быть вложенная папка приложения.

## Подготовка через программу

Во вкладке **Загрузка билда** укажите папку Projects и нажмите **Найти и подготовить**.
После изменения ключей поиск начинается автоматически. App ID можно не вводить:
программа получает список приложений Apple и сопоставляет Bundle ID с исходниками.
При нескольких совпадениях появится выбор; если совпадений нет — **Указать проект…**.
Поддерживаются явные Bundle ID в Xcode. Название папки может отличаться от имени приложения.

Программа создаёт переносимый YAML и эту инструкцию в корне найденного репозитория,
а также рабочий `.github/workflows/apple-automatic-ios.yml`. В YAML уже заполнены App ID,
Bundle ID, папка приложения и найденная схема. Название будущих сборок — **IOS BUILD**.
Проверка и подготовка не отправляют файлы в GitHub и не запускают сборку.
Отправьте файлы через GitHub Desktop, затем нажмите **Собрать и загрузить** в программе.
Защищённые ключи настроятся при запуске. Ручные изменения подготовленных файлов
программа сохраняет: при конфликте подготовка остановится с объяснением.

Для самостоятельной установки переносимого шаблона следуйте инструкции ниже.
Не добавляйте второй активный workflow, если рабочий файл уже создан программой.

## Подключение к новому проекту

1. В **корне GitHub-репозитория** создайте `.github/workflows/` и скопируйте туда
   шаблон под именем `universal-ios.yml`. Например:

   ```text
   MyRepository/
     .github/workflows/universal-ios.yml
     project/pubspec.yaml                # Flutter во вложенной папке
     project/ios/Runner.xcodeproj/
   ```

   Для Swift/Objective-C структура может выглядеть так:

   ```text
   MyRepository/
     .github/workflows/universal-ios.yml
     MyApp.xcodeproj/
     MyApp.xcodeproj/xcshareddata/xcschemes/MyApp.xcscheme
     Sources/
   ```

   Просто положить YAML рядом с приложением недостаточно: GitHub запускает
   workflow только из `.github/workflows/` в корне репозитория.
   Само приложение может оставаться в любой вложенной папке.

2. Добавьте четыре **Repository secrets** в GitHub → Settings → Secrets and
   variables → Actions:

   | Secret | Значение |
   |---|---|
   | `APP_STORE_CONNECT_ISSUER_ID` | Issuer ID аккаунта Apple |
   | `APP_STORE_CONNECT_KEY_IDENTIFIER` | Key ID |
   | `APP_STORE_CONNECT_PRIVATE_KEY` | Полное содержимое ключа `.p8`, включая BEGIN/END |
   | `CERTIFICATE_PRIVATE_KEY` | Полное содержимое приватного RSA-ключа PEM для сертификата подписи |

   Ключ подписи должен сохраняться между запусками. Если его ещё нет, создайте
   один RSA-ключ, например `openssl genrsa -out certificate-private-key.pem 2048`,
   сохраните его содержимое в secret и сам ключ храните приватно. Ключи не должны
   попадать в репозиторий. Apple API-ключу нужны права на приложение, сертификаты,
   provisioning profiles и загрузку сборок.

   У Apple Automatic имена Apple secrets привязаны к приложению/Key ID и имеют
   префикс `APPLE_AUTOMATIC_…`. Для самостоятельного шаблона нужны четыре имени
   из таблицы. При использовании программы ничего вручную переносить не нужно.

3. Отправьте workflow и исходники в основную ветку. Откройте **Actions → IOS BUILD → Run workflow**, выберите ветку и заполните:

   | Поле | Что указать |
   |---|---|
   | `bundle_id` | Например `com.company.app`, точно как в Xcode и App Store Connect |
   | `app_store_apple_id` | Числовой App ID приложения в App Store Connect |
   | `project_path` | `auto` или путь от корня репозитория: `.`, `project`, `apps/MyApp`, `ios` |
   | `xcode_scheme` | `auto` или имя общей схемы Xcode; для Flutter не требуется |
   | `xcode_container` | `auto` или путь от корня к `.xcworkspace`/`.xcodeproj`; для Flutter не требуется |
   | `flutter_version` | Версия Flutter; для Swift/Objective-C игнорируется |
   | `run_tests` | Запустить Flutter-тесты, если они есть |
   | `upload_to_testflight` | Выключите для сборки без отправки в Apple |

   Никакие данные Apple и названия конкретных приложений в шаблон не зашиты.
   Он запускается вручную; отправка коммита сама по себе не запускает публикацию.

## Что происходит при сборке

- Проверка наличия секретов до запуска macOS.
- Поиск приложения по Bundle ID, без папок зависимостей и примеров.
- При нескольких подходящих приложениях, контейнерах или схемах сборка
  останавливается с просьбой указать выбор явно.
- Установка Flutter-зависимостей или CocoaPods, если в нативной папке есть Podfile.
- Получение сертификатов/profiles через Codemagic CLI, доступный вне Codemagic.
- Номер билда выше последнего номера в Apple и последних IPA-артефактах GitHub.
  Ошибка запроса Apple останавливает процесс, номер не сбрасывается в 1.
- Сборка `.ipa`; проверка Bundle ID и номера билда **внутри готового архива**.
- Переименование готового файла в `app.ipa` без изменения содержимого и подписи.
  Двоеточия в названии самого приложения разрешены и не меняются.
- Сохранение IPA в GitHub и, если включено, загрузка в App Store Connect/TestFlight.

## Границы шаблона

Нативный проект должен содержать общую схему, добавленную в Git, и поддерживать
обновление версии через `agvtool`/`CURRENT_PROJECT_VERSION`. Используется Xcode из
образа `macos-26`; для проекта с жёсткой версией Xcode её нужно зафиксировать.
Нативные unit/UI-тесты добавляются отдельным шагом под симулятор/test plan проекта.

React Native, Expo, Unity, .NET MAUI и другие проекты с генерацией Xcode-проекта
или отдельной установкой зависимостей требуют своих подготовительных шагов.
Проекты с flavors, несколькими приложениями/расширениями или Bundle ID через
xcconfig также могут потребовать отдельной настройки схем и подписи. Это не
автоматическая поддержка любого фреймворка.

Перед первым рабочим запуском нативного проекта можно отключить отправку и
проверить получившийся IPA. Проверки шаблона покрывают поиск Flutter/Xcode,
неоднозначные пути и проверку IPA; реальные сертификаты и сборку каждого нового
проекта подтверждает его запуск в GitHub Actions.

Apple обрабатывает загруженный билд отдельно. Шаблон не отправляет приложение
на App Review и не выпускает его публично.

## Apple Automatic

Программа по-прежнему подключает обычные Flutter iOS проекты автоматически и
создаёт собственный `apple-automatic-ios.yml`, привязанный к выбранному аккаунту
и приложению. В её генераторе исправлено имя IPA и обновлён upload-artifact до
Node.js 24. Универсальный файл предназначен для самостоятельной сборки разных
проектов через GitHub Actions; он не заменяет файл, которым управляет программа.
Чтобы избежать двойной отправки, выбирайте один способ запуска конкретного билда.
